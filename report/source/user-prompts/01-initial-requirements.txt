Think critically. Challenge weak assumptions, investigate technical limitations, and justify architectural decisions. Do not build features merely because they sound impressive.

2. CONTEXT — WHAT WE ARE BUILDING
I want a Chrome extension that improves prompts directly inside editable text fields on websites.
The core experience should be:

1. The user types a prompt into a text field on a supported website.
2. The user activates the extension using a toolbar button, keyboard shortcut, or another approved interaction.
3. The extension captures the prompt from the active editable field.
4. An enhancement engine analyzes the prompt, identifies the task, and chooses suitable prompt engineering techniques.
5. The engine rewrites the prompt to improve clarity, structure, specificity, and expected output quality.
6. The enhanced prompt replaces the original text in the same field.
7. The user can inspect the result, undo the replacement, and restore the original prompt.
8. The user decides whether to submit the enhanced prompt.

The extension must never submit the prompt automatically.
The user should not need to open a separate dashboard or manually copy and paste prompts between applications.
The product should work across multiple supported websites, including AI chat interfaces, coding tools, writing applications, and research tools.
Do not promise compatibility with every website. Define a realistic support matrix and test actual editor behavior.
Core product philosophy
The extension should optimize for prompt effectiveness, not prompt length.
A short question should remain short when it is already effective. A complex task should receive more structure when that structure meaningfully improves the instructions.
The extension must preserve the user's intent, facts, terminology, constraints, and desired outcome.
It must not fabricate missing context, introduce arbitrary requirements, or change the user's objective.
3. OBJECTIVES — PRODUCT REQUIREMENTS
3.1 Prompt capture and replacement
The extension must:

* Detect the active editable field when enhancement is requested.
* Read its current text accurately.
* Preserve the original prompt before making any changes.
* Send only the necessary prompt content and explicitly approved context to the selected AI provider.
* Insert the enhanced prompt into the same field.
* Trigger the appropriate input events for supported websites.
* Preserve focus wherever possible.
* Avoid duplicate enhancement requests from repeated clicks.
* Allow the user to cancel or recover from failed requests where practical.
* Provide reliable undo and restoration of the original text.
* Never submit the prompt, click Send, or execute the user's instructions.

Investigate support for:

* HTML `textarea` elements.
* Text inputs.
* `contenteditable` elements.
* Rich-text editors.
* Framework-controlled inputs, including React-based applications.
* Shadow DOM where accessible.
* Iframes and cross-origin restrictions.
* Websites that replace their editor dynamically.

Use safe, supported techniques. Do not depend on brittle DOM manipulation or framework internals when a more reliable integration is available.
If an editor cannot be updated safely, explain the limitation and provide a non-destructive fallback where feasible.
3.2 Prompt enhancement engine
Design a modular enhancement pipeline with the following stages:

1. Input validation: Determine whether the active field contains a usable prompt.
2. Intent analysis: Identify what the user is trying to accomplish.
3. Task classification: Classify the task into categories such as coding, research, writing, analysis, factual question, planning, or creative work.
4. Quality analysis: Identify ambiguity, missing constraints, vague instructions, insufficient context, and unspecified output formats.
5. Framework selection: Select the most suitable framework or combination of techniques.
6. Prompt rewriting: Produce a clear, actionable, well-structured prompt.
7. Validation: Check that the result preserves intent and does not introduce unsupported facts or requirements.
8. Presentation: Return the enhanced prompt in a predictable format.
9. Replacement: Update the active editor only after a successful response and appropriate validation.

Keep these responsibilities logically separate.
Avoid unnecessary model calls. Determine which processing stages can be combined into a single request without sacrificing quality or maintainability.
3.3 Prompt engineering frameworks
The engine should understand and selectively apply the following frameworks and techniques:

* CO-STAR: Context, Objective, Style, Tone, Audience, Response.
* RISEN: Role, Instructions, Steps, End Goal, Narrowing.
* RTF: Role, Task, Format.
* CREATE: Context, Role, Explicit, Action, Target Audience, Exclusions.
* APE: Action, Purpose, Expectation.
* Role and perspective specification.
* Explicit instructions and step sequencing.
* Task decomposition.
* Context enrichment.
* Output format and schema specification.
* Few-shot examples when useful.
* Explicit success criteria.
* Scope boundaries and exclusions.
* Ambiguity reduction.
* Source-material delimitation.
* Appropriate handling of untrusted input.

Treat framework definitions as conventions that should be verified. Do not assume acronyms have universally standardized meanings.
Framework selection must be task-dependent. The engine must not mechanically force every prompt into CO-STAR or RISEN.
Examples:

* A simple factual question may need only clearer wording.
* A coding request may benefit from language, environment, constraints, expected behavior, and test requirements.
* A research request may need scope, evidence requirements, source expectations, and a structured output.
* A creative-writing request may benefit from audience, tone, style, and creative constraints.
* An analytical task may benefit from explicit evaluation criteria and output structure.

Create a framework registry or equivalent modular architecture so new frameworks and strategies can be added without rewriting the entire enhancement engine.
For each framework, define its intended use, selection criteria, instructions, limitations, and representative tests.
3.4 Enhancement modes
Plan for three levels of enhancement:

* Light: Correct ambiguity and improve clarity with minimal changes.
* Balanced: Improve instructions, context, constraints, and output format where useful.
* Deep: Apply more comprehensive task analysis, structure, decomposition, and success criteria when justified.

Balanced should be the default unless the technical evaluation supports another choice.
The selected mode should affect the enhancement strategy, not simply the length of the generated prompt.
Consider task-specific presets such as:

* General.
* Coding.
* Research.
* Writing.
* Analysis.
* Creative.

Keep these optional presets separate from the core enhancement engine.
For the MVP, implement only the settings necessary to validate the central experience. Do not overbuild the interface.

Both providers must be supported through a provider-neutral architecture.
The initial prototype should prioritize access through their available free API tiers, where eligible. Do not assume free access means unlimited usage, permanent availability, or permission for every deployment scenario.

4.2 Provider-neutral architecture
Create a shared provider interface so Groq and Gemini can be used interchangeably.
Separate:

* Enhancement pipeline.
* Framework selection.
* Shared enhancement instructions.
* Provider adapters.
* Request construction.
* Response parsing.
* Configuration.
* Credential management.
* Error handling.
* Response validation.

Do not scatter provider-specific conditionals throughout the application.
Provider-specific models, endpoints, and configuration should be centralized.
The user should be able to select a configured provider through the settings interface.
A future provider should be addable without rewriting the core enhancement engine.
4.3 API key management
For the personal-use prototype, support user-supplied API keys for Groq and Gemini.
The settings interface should allow the user to:

* Select a provider.
* Enter or update that provider's API key.
* Select from verified, supported models.
* Test provider connectivity where feasible.
* View understandable configuration and authentication errors.
* Remove a saved key.

Security requirements:

* Never hardcode real API keys into source code.
* Never commit real credentials to Git.
* Do not expose keys in URLs, logs, telemetry, error messages, or debugging output.
* Never treat a bundled `.env` file as secure once its contents are included in an extension build.
* Do not claim that Chrome extension storage makes provider keys inaccessible to malicious extensions or local users.
* Explain the security implications of saving API keys in browser extension storage.
* Request only necessary Chrome permissions.
* Avoid collecting or transmitting data unrelated to the enhancement request.

For the initial personal-use prototype, direct provider access using the user's own key is acceptable if the risks are documented and the architecture is designed appropriately.
For a public release, evaluate a backend proxy that keeps provider credentials off the client. Consider authentication, hosting expenses, rate limiting, abuse prevention, quotas, and operational maintenance.
Do not introduce a backend automatically. Recommend the simplest viable approach for the intended deployment.
4.4 Provider fallback and cost control
Allow the user to configure a default provider and, if practical, a manual alternative.
Do not silently send a user's prompt to another provider after a failure.
Any automatic provider fallback must be explicitly enabled, clearly explained, and limited to the configured providers.
Implement reasonable safeguards against:

* Infinite retries.
* Duplicate requests.
* Unnecessary model calls.
* Repeated quota failures.
* Excessive request sizes.
* Unexpected API usage.

Use bounded retries only when appropriate. Respect provider rate-limit guidance and distinguish transient failures from authentication or quota failures.
4.5 Consistent output
Both providers must follow the same core enhancement specification.
Use a predictable response contract that separates:

* Enhanced prompt text.
* Optional framework or task metadata.
* Validation status, if needed internally.

Do not expose provider-specific formatting to the user.
Validate responses before inserting them into an editor. If the response is empty, malformed, or otherwise unusable, preserve the original prompt and display an error.
Do not automatically replace the user's prompt with an unvalidated response.

The extension must remain useful without requiring users to understand prompt engineering frameworks.
6. SECURITY, PRIVACY, AND RELIABILITY
Use Chrome Extension Manifest V3.
Investigate the appropriate division of responsibilities between:

* Popup or extension UI.
* Content scripts.
* Background service worker.
* Storage.
* Provider adapters.
* Optional backend.

Do not give content scripts or the service worker unnecessary responsibilities or permissions.
Required safeguards

1. Request only the permissions required by the selected architecture.
2. Prefer narrow host permissions where feasible.
3. Avoid broad access to all websites unless the design genuinely requires it and the permissions are clearly justified.
4. Never transmit page content unrelated to the active prompt.
5. Do not transmit the full page or conversation history by default.
6. Treat website content and user-provided material as untrusted input.
7. Do not let prompt text override application-level security rules or cause unintended tool execution.
8. Do not execute model-generated code or scripts.
9. Keep API credentials out of logs and distributed source.
10. Avoid unnecessary analytics and telemetry.
11. Document what information is transmitted to Groq or Gemini.
12. Provide appropriate user disclosure before external processing.
13. Handle provider failures without destroying the user's original text.
14. Do not claim that extension-side prompt instructions provide a security boundary against a malicious model response.

Distinguish the security of the application's own behavior from prompt injection risks within text being rewritten.
Document any remaining risks that cannot be eliminated by the proposed architecture.

8. PROMPT QUALITY EVALUATION
A successful enhancement is not necessarily a longer or more elaborate prompt.
Design a test dataset containing representative examples such as:

* A simple factual question.
* An underspecified coding task.
* A research request.
* A professional writing request.
* A creative task.
* A complex analytical task.
* A prompt with explicit constraints that must be preserved.
* A prompt that is already well-written.
* A prompt containing insufficient information.
* A prompt containing adversarial or untrusted quoted text.

Evaluate the following dimensions:

1. Intent preservation.
2. Factual and constraint preservation.
3. Clarity.
4. Specificity.
5. Relevance of added structure.
6. Output-format clarity.
7. Conciseness.
8. Absence of invented requirements.
9. Framework-selection appropriateness.
10. Failure safety.

Define measurable acceptance criteria and compare Groq and Gemini against the same dataset.
Include regression tests so changes to the enhancement instructions do not silently degrade prompt quality.
Use a combination of deterministic assertions and documented human evaluation. Do not pretend a subjective prompt-quality score is an objective guarantee of model performance.
Set a reasonable response-time target for the MVP and explain how it will be measured.
